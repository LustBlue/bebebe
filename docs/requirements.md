# Требования к модулям системы ProjectFlow

## Информационная система управления проектами

**Версия:** 1.0  
**Дата:** 06.10.2026  
**Авторы:** Проектная команда ProjectFlow

---

## 1. Введение

### 1.1 Цель документа

Настоящий документ определяет требования к трём основным программным модулям информационной системы управления проектами «ProjectFlow»:
- Модуль авторизации пользователей (AuthModule)
- Модуль управления задачами (TaskModule)
- Модуль формирования отчётов (ReportModule)

### 1.2 Область применения

Система ProjectFlow предназначена для управления проектами и задачами в организациях любого масштаба. Система обеспечивает:
- Централизованное управление пользователями и их ролями
- Создание и отслеживание задач с различными статусами
- Формирование аналитических отчётов по различным критериям

### 1.3 Нормативные ссылки

- ГОСТ 34.602-2020 «Информационные технологии. Комплекс стандартов на автоматизированные системы»
- ISO/IEC 25010:2011 «System and software quality models»
- RFC 7519 «JSON Web Token (JWT)»
- ISO/IEC 27001:2013 «Информационная безопасность»

## 2. Общие требования к системе

### 2.1 Архитектура

Система построена по модульной архитектуре с чётким разделением ответственности:

```
┌─────────────────────────────────────┐
│        REST API (Flask)             │
├─────────────────────────────────────┤
│  AuthModule │ TaskModule │ ReportModule │
├─────────────────────────────────────┤
│         Core Components              │
│  (Database, Security, Config)        │
├─────────────────────────────────────┤
│       SQLite Database                │
└─────────────────────────────────────┘
```

### 2.2 Технологический стек

- **Язык программирования:** Python 3.10+
- **Веб-фреймворк:** Flask 3.0
- **База данных:** SQLite/PostgreSQL
- **Аутентификация:** JWT (JSON Web Tokens)
- **Тестирование:** pytest
- **Статический анализ:** pylint, flake8

### 2.3 Роли пользователей

Система поддерживает три роли с различными уровнями доступа:

1. **Администратор (admin):**
   - Полный доступ ко всем функциям системы
   - Управление пользователями и их ролями
   - Деактивация пользователей

2. **Менеджер (manager):**
   - Создание и управление проектами
   - Создание задач и назначение исполнителей
   - Изменение статусов задач
   - Формирование отчётов

3. **Исполнитель (executor):**
   - Просмотр назначенных задач
   - Изменение статусов своих задач
   - Просмотр отчётов по своим задачам

## 3. Модуль авторизации (AuthModule)

### 3.1 Назначение модуля

Модуль AuthModule отвечает за аутентификацию и авторизацию пользователей, управление учётными записями и ролями, а также восстановление доступа к системе.

### 3.2 Функциональные требования

#### 3.2.1 Регистрация пользователей

**Идентификатор:** AUTH-FR-001  
**Описание:** Система должна обеспечивать регистрацию новых пользователей

**Входные данные:**
- Имя пользователя (username) — строка, 3-50 символов, уникальное
- Email — строка, валидный формат email, уникальный
- Пароль — строка, минимум 8 символов, должен содержать буквы разных регистров и цифры
- Роль — один из: admin, manager, executor (по умолчанию executor)

**Выходные данные:**
- ID созданного пользователя
- Данные пользователя (без пароля)
- HTTP статус 201 Created

**Бизнес-правила:**
- Пароль должен хешироваться перед сохранением (PBKDF2-HMAC-SHA256)
- Имя пользователя и email должны быть уникальными
- Роль admin может быть назначена только администратором

**Исключительные ситуации:**
- Дубликат имени пользователя или email → HTTP 400, ValidationError
- Слабый пароль → HTTP 400, ValidationError
- Невалидный email → HTTP 400, ValidationError

#### 3.2.2 Вход в систему

**Идентификатор:** AUTH-FR-002  
**Описание:** Система должна обеспечивать вход пользователей с выдачей JWT токенов

**Входные данные:**
- Имя пользователя или email
- Пароль

**Выходные данные:**
- Access токен (срок действия 1 час)
- Refresh токен (срок действия 7 дней)
- Данные пользователя
- HTTP статус 200 OK

**Бизнес-правила:**
- Токены должны быть подписаны секретным ключом
- Access токен содержит: user_id, role, exp, iat, type='access'
- Refresh токен содержит: user_id, exp, iat, type='refresh'
- Деактивированные пользователи не могут войти в систему

**Исключительные ситуации:**
- Неверные учётные данные → HTTP 401, AuthenticationError
- Деактивированный пользователь → HTTP 401, AuthenticationError

#### 3.2.3 Обновление токена

**Идентификатор:** AUTH-FR-003  
**Описание:** Система должна обеспечивать обновление access токена по refresh токену

**Входные данные:**
- Refresh токен

**Выходные данные:**
- Новый access токен
- HTTP статус 200 OK

**Исключительные ситуации:**
- Невалидный токен → HTTP 401, AuthenticationError
- Истёкший токен → HTTP 401, AuthenticationError

#### 3.2.4 Восстановление пароля

**Идентификатор:** AUTH-FR-004  
**Описание:** Система должна обеспечивать сброс пароля через токен

**Шаг 1: Запрос токена**
- Входные данные: email
- Выходные данные: токен сброса (срок действия 1 час)

**Шаг 2: Сброс пароля**
- Входные данные: токен сброса, новый пароль
- Выходные данные: подтверждение успешного сброса

#### 3.2.5 Управление ролями

**Идентификатор:** AUTH-FR-005  
**Описание:** Администратор может изменять роли пользователей

**Требования доступа:** Только роль admin

**Входные данные:**
- ID пользователя
- Новая роль

**Исключительные ситуации:**
- Недостаточно прав → HTTP 403, PermissionError

### 3.3 API Endpoints

| Метод | Путь | Описание | Роль |
|-------|------|----------|------|
| POST | /api/auth/register | Регистрация пользователя | Открытый |
| POST | /api/auth/login | Вход в систему | Открытый |
| POST | /api/auth/refresh | Обновление токена | Открытый |
| POST | /api/auth/reset-password | Запрос сброса пароля | Открытый |
| POST | /api/auth/reset-password/{token} | Сброс пароля | Открытый |
| GET | /api/auth/me | Текущий пользователь | Авторизованный |
| PUT | /api/auth/users/{id}/role | Обновление роли | admin |
| POST | /api/auth/users/{id}/deactivate | Деактивация | admin |

### 3.4 Нефункциональные требования

- **Безопасность:** Пароли хешируются с использованием PBKDF2-HMAC-SHA256 с 120000 итерациями
- **Производительность:** Время регистрации/входа не должно превышать 500 мс
- **Надёжность:** Все операции с базой данных выполняются в транзакциях

## 4. Модуль управления задачами (TaskModule)

### 4.1 Назначение модуля

Модуль TaskModule обеспечивает создание, редактирование, удаление задач, управление их статусами, назначение исполнителей и отслеживание истории изменений.

### 4.2 Статусы задач и переходы

Задача в системе может находиться в одном из следующих статусов:

```
   ┌─────┐
   │ new │ ────────────┐
   └──┬──┘             │
      │                │
      ▼                │
 ┌────────────┐        │
 │in_progress │        │
 └─────┬──────┘        │
       │               │
       ▼               ▼
   ┌───────┐      ┌──────────┐
   │review │ ───► │rejected  │
   └───┬───┘      └────┬─────┘
       │               │
       ▼               │
  ┌─────────┐          │
  │completed│          │
  └─────────┘          │
       ▲               │
       └───────────────┘
```

**Допустимые переходы:**
- new → in_progress, rejected
- in_progress → review, rejected
- review → completed, in_progress, rejected
- rejected → new
- completed → (конечное состояние, переходы недопустимы)

### 4.3 Функциональные требования

#### 4.3.1 Создание задачи

**Идентификатор:** TASK-FR-001  
**Описание:** Система должна обеспечивать создание новых задач

**Входные данные:**
- Заголовок — строка, 1-150 символов, обязательно
- Описание — текст, опционально
- ID проекта — целое число, обязательно
- ID создателя — целое число, обязательно
- ID исполнителя — целое число, опционально
- Приоритет — один из: low, normal, high, critical (по умолчанию normal)
- Срок выполнения — дата в формате ISO 8601, опционально

**Выходные данные:**
- Созданная задача со статусом 'new'
- HTTP статус 201 Created

**Бизнес-правила:**
- Создатель должен быть авторизован
- Проект должен существовать
- Исполнитель (если указан) должен быть активным пользователем
- При создании задачи автоматически создаётся запись в истории

**Исключительные ситуации:**
- Проект не найден → HTTP 400, ValidationError
- Исполнитель не найден → HTTP 400, ValidationError
- Недопустимый приоритет → HTTP 400, ValidationError

#### 4.3.2 Получение задач

**Идентификатор:** TASK-FR-002  
**Описание:** Система должна обеспечивать получение списка задач с фильтрацией

**Параметры фильтрации:**
- project_id — фильтр по проекту
- assigned_to — фильтр по исполнителю
- status — фильтр по статусу
- limit — максимальное количество записей (по умолчанию 100)
- offset — смещение для пагинации (по умолчанию 0)

**Выходные данные:**
- Массив задач с полной информацией
- HTTP статус 200 OK

#### 4.3.3 Обновление задачи

**Идентификатор:** TASK-FR-003  
**Описание:** Система должна обеспечивать обновление данных задачи

**Требования доступа:**
- Создатель задачи
- Исполнитель задачи
- Пользователи с ролью manager или admin

**Обновляемые поля:**
- Заголовок
- Описание
- Приоритет
- Срок выполнения

**Исключительные ситуации:**
- Недостаточно прав → HTTP 403, PermissionError

#### 4.3.4 Изменение статуса задачи

**Идентификатор:** TASK-FR-004  
**Описание:** Система должна обеспечивать изменение статуса задачи с контролем допустимых переходов

**Входные данные:**
- ID задачи
- Новый статус
- ID пользователя

**Бизнес-правила:**
- Переход должен быть допустимым согласно диаграмме состояний
- При каждом изменении статуса создаётся запись в истории
- Из статуса 'completed' переходы невозможны

**Исключительные ситуации:**
- Недопустимый переход → HTTP 400, ValidationError

#### 4.3.5 Назначение исполнителя

**Идентификатор:** TASK-FR-005  
**Описание:** Система должна обеспечивать назначение/изменение исполнителя задачи

**Требования доступа:** Только роли manager и admin

**Входные данные:**
- ID задачи
- ID исполнителя

**Исключительные ситуации:**
- Недостаточно прав → HTTP 403, PermissionError
- Исполнитель не найден → HTTP 400, ValidationError

#### 4.3.6 Удаление задачи

**Идентификатор:** TASK-FR-006  
**Описание:** Система должна обеспечивать удаление задач

**Требования доступа:**
- Создатель задачи
- Пользователи с ролью manager или admin

**Бизнес-правила:**
- При удалении задачи каскадно удаляется история изменений

### 4.4 API Endpoints

| Метод | Путь | Описание | Роль |
|-------|------|----------|------|
| GET | /api/tasks | Получить список задач | Авторизованный |
| POST | /api/tasks | Создать задачу | Авторизованный |
| GET | /api/tasks/{id} | Получить задачу | Авторизованный |
| PUT | /api/tasks/{id} | Обновить задачу | Создатель/Исполнитель/Manager/Admin |
| DELETE | /api/tasks/{id} | Удалить задачу | Создатель/Manager/Admin |
| PATCH | /api/tasks/{id}/status | Изменить статус | Авторизованный |
| PATCH | /api/tasks/{id}/assign | Назначить исполнителя | Manager/Admin |
| GET | /api/tasks/{id}/history | История изменений | Авторизованный |

### 4.5 Нефункциональные требования

- **Производительность:** Получение списка из 100 задач не должно превышать 200 мс
- **Целостность:** Все изменения статусов записываются в историю
- **Валидация:** Все переходы статусов проверяются на допустимость

## 5. Модуль формирования отчётов (ReportModule)

### 5.1 Назначение модуля

Модуль ReportModule обеспечивает формирование аналитических отчётов по задачам с различными критериями группировки и экспорт отчётов в форматы PDF и Excel.

### 5.2 Функциональные требования

#### 5.2.1 Отчёт по исполнителю

**Идентификатор:** REPORT-FR-001  
**Описание:** Система должна формировать отчёт о задачах конкретного исполнителя

**Входные данные:**
- ID исполнителя — обязательно
- Дата начала периода — опционально
- Дата окончания периода — опционально

**Выходные данные:**
- Информация об исполнителе
- Общая статистика:
  - Общее количество задач
  - Распределение по статусам
  - Распределение по приоритетам
- Детальный список задач
- HTTP статус 200 OK

**Бизнес-правила:**
- Учитываются только задачи, назначенные данному исполнителю
- Если период не указан, учитываются все задачи

#### 5.2.2 Отчёт по проекту

**Идентификатор:** REPORT-FR-002  
**Описание:** Система должна формировать отчёт о задачах в проекте

**Входные данные:**
- ID проекта — обязательно
- Дата начала периода — опционально
- Дата окончания периода — опционально

**Выходные данные:**
- Информация о проекте
- Общая статистика:
  - Общее количество задач
  - Распределение по статусам
  - Распределение по исполнителям
- Детальный список задач
- HTTP статус 200 OK

#### 5.2.3 Отчёт за период

**Идентификатор:** REPORT-FR-003  
**Описание:** Система должна формировать отчёт о всех задачах за указанный период

**Входные данные:**
- Дата начала периода — обязательно
- Дата окончания периода — обязательно

**Выходные данные:**
- Общая статистика:
  - Общее количество задач
  - Распределение по статусам
  - Распределение по проектам
  - Распределение по приоритетам
- Детальный список задач
- HTTP статус 200 OK

#### 5.2.4 Экспорт в Excel

**Идентификатор:** REPORT-FR-004  
**Описание:** Система должна экспортировать отчёт в формат Excel (.xlsx)

**Входные данные:**
- Данные отчёта (JSON)

**Выходные данные:**
- Путь к созданному файлу
- HTTP статус 200 OK

**Требования к формату:**
- Заголовок отчёта с типом и периодом
- Раздел статистики
- Таблица задач с колонками: ID, Название, Статус, Приоритет, Создано
- Форматирование: жирный шрифт для заголовков, фон для шапки таблицы

#### 5.2.5 Экспорт в PDF

**Идентификатор:** REPORT-FR-005  
**Описание:** Система должна экспортировать отчёт в формат PDF

**Входные данные:**
- Данные отчёта (JSON)

**Выходные данные:**
- Путь к созданному файлу
- HTTP статус 200 OK

**Требования к формату:**
- Титульный лист с названием отчёта
- Информация о периоде
- Статистические данные
- Таблица задач (до 50 записей на страницу)

### 5.3 API Endpoints

| Метод | Путь | Описание | Роль |
|-------|------|----------|------|
| GET | /api/reports/by-user/{user_id} | Отчёт по исполнителю | Авторизованный |
| GET | /api/reports/by-project/{project_id} | Отчёт по проекту | Авторизованный |
| GET | /api/reports/by-period | Отчёт за период | Авторизованный |
| POST | /api/reports/export/excel | Экспорт в Excel | Авторизованный |
| POST | /api/reports/export/pdf | Экспорт в PDF | Авторизованный |
| GET | /api/reports | Список отчётов | Авторизованный |

### 5.4 Нефункциональные требования

- **Производительность:** Формирование отчёта на 1000 задач не должно превышать 2 секунды
- **Ограничения:** PDF экспорт ограничен 50 задачами на страницу для оптимизации размера файла
- **Хранение:** Все сформированные отчёты сохраняются в директории `./reports`

### 6.2 Передача данных между модулями

#### 6.2.1 AuthModule → TaskModule
- **Контекст:** При создании/изменении задач

#### 6.2.2 AuthModule → ReportModule
- **Контекст:** При формировании отчётов
- **Данные:** user_id (из JWT токена)
- **Назначение:** Идентификация создателя отчёта

#### 6.2.3 TaskModule → ReportModule
- **Контекст:** При формировании отчётов
- **Данные:** Задачи, история изменений
- **Назначение:** Источник данных для отчётов

### 6.3 События и уведомления

| Событие | Инициатор | Обработчики | Действие |
|---------|-----------|-------------|----------|
| Создание задачи | TaskModule | TaskModule | Создание записи в task_history |
| Изменение статуса | TaskModule | TaskModule | Добавление записи в историю |
| Деактивация пользователя | AuthModule | - | Запрет входа в систему |

## 7. Требования к безопасности

### 7.1 Аутентификация и авторизация
- Все пароли хешируются с использованием PBKDF2-HMAC-SHA256
- JWT токены подписываются секретным ключом (HS256)
- Access токены имеют ограниченный срок действия (1 час)
- Refresh токены хранятся на клиенте и используются для обновления access токенов

### 7.2 Защита данных
- SQL-инъекции предотвращаются использованием параметризованных запросов
- Секретные ключи хранятся в переменных окружения
- Пароли никогда не возвращаются в API ответах

### 7.3 Контроль доступа
- Все API endpoints (кроме публичных) требуют валидный JWT токен
- Ролевой контроль доступа (RBAC) реализован на уровне декораторов
- Пользователи могут изменять только свои данные (кроме admin и manager)
