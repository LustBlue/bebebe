# Тестовые наборы и сценарии

**Проект:** ProjectFlow — информационная система управления проектами
**Объект тестирования:** AuthModule, TaskModule, ReportModule, слой интеграции (`src/api.py`, `src/core/http_core.py`)
**Вид практики:** производственная практика ПП.02

---

## 1. Назначение и область применения

Настоящий документ описывает тестовые наборы и сценарии проверки программных
модулей информационной системы ProjectFlow. Документ предназначен для включения
в отчёт о производственной практике в качестве раздела «Тестовые наборы и
сценарии» и является методической основой автоматизированного и ручного
тестирования системы.

**Объект проверки:**

* модуль авторизации и управления пользователями (AuthModule,
  `src/auth_module/__init__.py`);
* модуль управления проектами и задачами (TaskModule,
  `src/task_module/__init__.py`, справочник проектов `src/core/projects_repo.py`);
* модуль формирования и экспорта отчётов (ReportModule,
  `src/report_module/__init__.py`, генератор PDF `src/report_module/pdf_writer.py`);
* слой интеграции модулей и REST API (`src/api.py`, `src/core/http_core.py`);
* общее ядро: конфигурация, подключение к БД, безопасность, валидация, модели
  предметной области (`src/core/`).

**Что проверяется:**

1. Корректность выполнения функций модулей на валидных данных (позитивные
   проверки).
2. Реакция на некорректные данные, отсутствующие сущности и нарушение прав
   доступа (негативные проверки).
3. Поведение на границах допустимых диапазонов значений (граничные проверки).
4. Соответствие реализованной диаграммы состояний задачи её математической
   модели — покрытие по критерию «все переходы».
5. Согласованность модулей при совместной работе через единое хранилище данных
   и единый механизм аутентификации.
6. Контракт REST API: коды состояния HTTP, структура JSON-ответов и
   JSON-ошибок.

**Методическая основа:**

* ГОСТ Р ИСО/МЭК 12207 — процессы жизненного цикла программных средств
  (процессы верификации и квалификационного тестирования);
* ГОСТ 34.601-90 — стадии и этапы создания автоматизированных систем
  (этап испытаний);
* ISO/IEC/IEEE 29148:2018 — требования и критерии приёмки, обеспечивающие
  проверяемость требований;
* ISO/IEC 25010:2011 — модель качества программного продукта (функциональная
  полнота, надёжность, защищённость, сопровождаемость);
* IEEE 830 — исторический стандарт на спецификацию требований, применённый как
  источник формы изложения критериев приёмки;
* внутренние документы проекта: `docs/requirements.md`,
  `docs/transition_matrix.md`, `docs/mathematical_models.md`.

## 2. Методика тестирования

### 2.1. Уровни тестирования

| Уровень | Что проверяется | Средства |
|---|---|---|
| Модульное (unit) | отдельные функции модулей: `register_user()`, `login_user()`, `create_task()`, `change_task_status()`, `generate_report_by_user()` и другие | тестовые функции `tests/test_*.py`, изолированная БД |
| Интеграционное | совместная работа модулей: JWT, выданный AuthModule, принимается TaskModule и ReportModule; данные задач используются при построении отчётов; единое хранилище SQLite | фикстуры `tests/conftest.py`, тесты `tests/test_integration.py` |
| Системное | приложение целиком через реальный HTTP-сервер: маршрутизация, коды ответов, экспорт файлов | `tests/test_integration.py` (класс `_ApiClient`, HTTP-сервер на свободном порту), `tools/smoke_test.py` |

### 2.2. Виды проверок

* **Функциональные** — подтверждают выполнение требования на валидных данных.
* **Негативные** — подтверждают корректную обработку ошибок: невалидные данные,
  несуществующие сущности, недопустимые переходы, отсутствие прав.
* **Граничные** — проверяют значения на границах и за границами допустимых
  диапазонов.
* **Проверки переходов состояний** — покрытие всех допустимых переходов
  диаграммы состояний задачи и отклонение запрещённых.
* **Проверки безопасности** — аутентификация по JWT, разграничение доступа по
  ролям (RBAC), отсутствие паролей и хешей в ответах API.
* **Регрессионные** — повторный прогон полного набора после изменений кода; в
  проекте выполняется автоматически в конвейере CI
  (`.github/workflows/ci.yml`) для Python 3.10, 3.11 и 3.12.

### 2.3. Техники проектирования тестов

**Классы эквивалентности.** Для каждого входного поля выделены классы валидных
и невалидных значений, и каждый класс представлен минимальным числом проверок:

| Поле | Валидные классы | Невалидные классы |
|---|---|---|
| `username` | 3–50 символов: латинские буквы, цифры, `_`, `.`, `-` | пусто; короче 3; длиннее 50; недопустимые символы (пробел, кириллица); дубликат существующего имени |
| `email` | соответствует шаблону `user@example.com` (непустая локальная часть, домен, зона из букв длиной не менее 2) | без `@`; без точки в домене; с пробелами; дубликат существующего адреса |
| `password` | не менее 8 символов, содержит заглавную и строчную буквы и цифру | короче 8 символов; без заглавной буквы; без строчной буквы; без цифры |
| `role` | `admin`, `manager`, `executor` (пустое значение → `executor`) | любое иное значение |
| `priority` | `low`, `normal`, `high`, `critical` (пустое значение → `normal`) | любое иное значение |
| `status` | `new`, `in_progress`, `review`, `completed`, `rejected` | любое иное значение; недопустимый переход из текущего состояния |
| `project_id`, `assigned_to`, `user_id` | идентификатор существующей записи | несуществующий идентификатор; ноль или отрицательное число; нечисловое значение |
| период отчёта | `start_date` ≤ `end_date`, формат `YYYY-MM-DD` | `start_date` > `end_date`; неверный формат; отсутствие обязательного параметра |

**Анализ граничных значений.** Проверяются значения на границах диапазонов:
длина имени пользователя 3 и 50 символов (и 2 и 51 — вне диапазона), длина
пароля 8 символов (и 7 — вне политики), длина заголовка задачи 1 и 150 символов
(и 151 — вне диапазона), параметры пагинации `limit` (по умолчанию 100) и
`offset` (по умолчанию 0), границы периода отчёта, совпадающие даты начала и
окончания.

**Тестирование переходов состояний (state-transition testing).** Матрица
допустимых переходов задана моделью предметной области
(`src/core/models.py`, `STATUS_TRANSITIONS`) и содержит 8 переходов между
5 статусами. Применён критерий покрытия «все переходы» (all-transitions):
каждый разрешённый переход выполняется как минимум одним сценарием, а
запрещённые переходы проверяются негативными сценариями. Детальная матрица
приведена в `docs/transition_matrix.md`.

### 2.4. Тестовое окружение

| Компонент | Значение |
|---|---|
| Язык и версия | Python 3.12 (поддерживаются 3.10+) |
| СУБД | SQLite (файл БД, режим WAL, включённые внешние ключи) |
| Внешние зависимости для тестирования | не требуются: набор выполняется средствами стандартной библиотеки |
| Встроенный запускающий модуль | `tools/run_tests.py` |
| Заглушка pytest | `tools/pytest_stub.py` (реализует `fixture`, `mark`, `raises`, `approx`, `Skipped` и параметризацию) |
| Альтернативный запуск | `pytest` — работает, если установлен; конфигурация задана в `pytest.ini` |
| Изоляция данных | фикстуры `tests/conftest.py`: `make_isolated_database()`, `temp_database`, `users`, `project`, `auth_header`; для системных проверок — HTTP-сервер на свободном порту с временной БД |
| Отчётность | протокол испытаний в формате Markdown или JSON (ключ `--summary`) |

Набор автоматических проверок размещён в каталоге `tests/`:

| Файл | Содержание |
|---|---|
| `tests/conftest.py` | общие фикстуры: изолированная БД, набор пользователей, проект, заголовок авторизации |
| `tests/test_auth_module.py` | 17 проверок AuthModule |
| `tests/test_task_module.py` | 21 проверка TaskModule, включая покрытие матрицы переходов |
| `tests/test_report_module.py` | 13 проверок ReportModule |
| `tests/test_integration.py` | 34 интеграционные и системные проверки, сквозные сценарии через HTTP |

## 6. Результаты выполнения

Автоматизированный набор выполняется командой `python -m tools.run_tests`.
Итоговые показатели (общее число проверок, число пройденных, не пройденных,
ошибок и пропущенных, а также перечень выполненных тестов по модулям) выводит
сам запускающий модуль и сохраняет в протокол испытаний
`reports/test_run_summary.md`. Документ формируется штатным ключом
`--summary` и содержит дату запуска, версию интерпретатора, платформу и таблицу
результатов по тестовым модулям.

Конкретные значения числа тестов и доли успешных проверок в настоящем документе
не приводятся: они фиксируются в протоколе испытаний
`reports/test_run_summary.md`, который формируется при каждом прогоне и
прикладывается к отчёту о практике. Такой порядок исключает расхождение между
описанием сценариев и фактическими результатами запуска.

Результаты сквозной проверки работающего приложения через HTTP фиксируются
отдельно инструментом `tools/smoke_test.py`: журнал проверок сохраняется в
`reports/smoke_test_report.json` (ключ `--json`).

## 7. Инструмент запуска

**Запуск полного набора автоматических тестов (средствами стандартной
библиотеки, без установки pytest):**

```
python -m tools.run_tests
```

**Запуск только проверок модуля авторизации (фильтр по имени теста):**

```
python -m tools.run_tests -k auth
```

**Запуск набора через pytest (если pytest установлен):**

```
python -m pytest tests/ -v
```

**Сквозная проверка работающего приложения по адресу запущенного сервера:**

```
python tools/smoke_test.py --base-url http://127.0.0.1:5000
```

Дополнительные возможности запускающего модуля:

| Команда | Назначение |
|---|---|
| `python -m tools.run_tests -q` | краткий вывод без построчной детализации |
| `python -m tools.run_tests tests/test_task_module.py` | запуск отдельного файла тестов |
| `python -m tools.run_tests --summary reports/test_run_summary.md` | сохранение протокола испытаний в формате Markdown |
| `python -m tools.run_tests --summary reports/test_run_summary.json --summary-format json` | сохранение протокола в формате JSON |
| `python tools/smoke_test.py --json reports/smoke_test_report.json` | сохранение журнала сквозной проверки |

Код возврата запускающего модуля равен нулю, если не пройденных тестов и ошибок
выполнения нет; это позволяет использовать его в конвейере CI
(`.github/workflows/ci.yml`).
